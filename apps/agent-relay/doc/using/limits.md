# Current limits and evolution options

**Utility:** collects current product, operational and delivery boundaries with practical handling and coherent evolution options.  
**Usage:** consult the relevant section when a workflow reaches a boundary; these options are proposals, not delivered features or a committed roadmap.

## How to read this register

Installed support, project permissions, user authorization and native-client permissions all matter. Increasing a numerical limit does not supply a missing adapter or permission. An architectural port is an extension point, not an implemented connector. Existing policies remain in force while an option is evaluated.

Some boundaries protect a deliberate priority: explicit authority, retained uncertainty, bounded resource use or minimal interference with the user's tools. Improvements must preserve that priority. The register covers known functional/operational limits and qualification gaps; individual schema validations remain in the tool contract rather than being duplicated here.

## Environments, clients and authority

| Current boundary and effect | Available handling | Possible evolution or chosen priority |
| --- | --- | --- |
| The shipped host/UI is Windows x64. Native agent connectors cover Codex and Claude in WSL; SSH, Gemini, OpenCode and other combinations are not delivered adapters. | Discover installed support and actual project grants; select a supported binding. | Implement and qualify additional client connectors and environment adapters through the existing ports. A non-Windows host also needs platform-specific credential/storage/composition support and an appropriate frontend. |
| A client's remote-control interface can be an entry point to MCP delegation; Relay does not turn every native tool or screen into a shared remote-control service. | Use the approved entry client to invoke available relay tools; downstream agents retain their own client capabilities and permissions. | Add explicit capability discovery and dedicated tools/adapters for genuinely needed remote actions, with authentication and scope checks. Preserve the priority of deliberate delegation over implicit cross-client privilege sharing. |
| The native WSL-side MCP exposes outbound messages, not a command channel to Windows. | Send a report/question/reply; Windows-side work needs its own authorized action. Received text is never executed as a command. | A separately approved reverse-operation protocol could use typed requests, explicit capabilities and native approval handling. Do not repurpose messages as executable instructions; directionality currently prioritizes a narrow authority boundary. |
| Ordinary scoped MCP cannot deploy a host, create a project or grant itself permissions. | Use separately authorized local administration/UI, then a scoped participant connection. | An optional administration adapter could expose narrowly authorized management operations and reviewable proposals under a distinct administrative identity. Retain the separation from ordinary participant rights. |
| Membership/DPAPI checks do not isolate the relay from arbitrary processes running under the same Windows account or from OS administrators. Revocation cannot undo started external effects. | Treat the local administrator/account as trusted; use narrow grants and inspect already dispatched work. | Qualify separate OS/service identities, restricted execution environments or remote authenticated boundaries when that stronger threat model is required. The current priority is local usability with explicit application-level authority. |
| Native runtime preparation needs dedicated owned folders; arbitrary existing agent conversations are not attached automatically. Adapter configuration may impose native tool restrictions. | Use a dedicated session and authorized existing workspace, respecting its instructions and the user's organization. | Add an explicitly opted-in attach/resume adapter only if ownership, inherited instructions, approval state and native-session identity can be established. Preserve isolation rather than silently adopting unrelated sessions. |

## Sessions, recovery and capacity

| Current boundary and effect | Available handling | Possible evolution or chosen priority |
| --- | --- | --- |
| One relay operation runs per session. Host concurrency defaults to 4 and accepts 1–64; excess work is refused as busy rather than queued. | Reuse a session sequentially or choose independent authorized sessions; adjust capacity after workload assessment. | Add a bounded scheduler with visible queue state, cancellation and per-project fairness. Benchmark any higher capacity instead of merely removing the bounds. |
| Shared-workspace leases coordinate this relay process, not unrelated terminals or other applications. | Avoid simultaneous manual/agent writes to the same resources; enable concurrent writes only deliberately. | Integrate connector-aware leases or isolated worktrees/snapshots with conflict handling where appropriate. External editors need cooperation; no relay lease alone can control them. |
| Interruption/cancellation is a request, not rollback. A timeout, disconnect or crash can leave work unknown; dispatch/receipt persistence cannot make arbitrary external effects transactional. | Inspect retained results/events and authoritative receipts before deciding on a new attempt. Never automatically replay uncertain work with a new ID. | Add connector-specific reconciliation and external idempotency/transaction support where available. Keep unknown when confirmation is unavailable: honest uncertainty is preferred to a false success or duplicate execution. |
| Native readiness, login, approvals, client CLI changes and provider quotas can block a task. Model-free startup does not prove the next model request will succeed. | Inspect readiness for the actual task; name missing account login clearly and request the account holder's action only when needed. | Strengthen versioned capability probes and typed authentication/quota diagnostics per connector; qualify compatible versions. Account authentication/approvals remain the user's authority rather than a workaround to automate around them. |
| A model may omit an independent progress message, and a received reply is not automatically an independently authored report. | Distinguish correlated replies from independent messages; use retained operation state for execution follow-up. | Offer an opt-in reporting policy or connector-native progress events, with provenance kept distinct from model-authored text. Preserve the user's working style and avoid mandatory extra model turns. |
| Technical settings bound profile/command counts (20 profiles and 100 configured commands per profile), as well as command argument lengths. | Keep configuration deliberate and use configured identifiers, not arbitrary shell text. | Revisit validated bounds or add searchable/paged configuration after a concrete scale need. Preserve predictable configuration and prevent unbounded input rather than promise unlimited command execution. |

## Files and filesystem crossings

| Current boundary and effect | Available handling | Possible evolution or chosen priority |
| --- | --- | --- |
| A transfer is one file between authorized Windows/local and WSL artifacts, attached to the selected session. There is no directory synchronization or arbitrary endpoint-to-endpoint copy. | Select explicit source/destination workspaces and relative paths; verify the retained result. | Add batch/directory manifests with per-file permissions, outcomes and replacement rules; later add other byte adapters. Synchronization needs explicit conflict/deletion semantics, not just recursive copy. |
| The default policy is 256 MiB per file, configurable from 1 byte to 4 GiB. Default wait is 180 seconds, configurable 30–3600 seconds; helper hashing shares the budget. | Configure an authorized workload deliberately and check free space/deadlines; size alone does not establish acceptable performance. | Qualify larger workloads, then consider bounded chunk streaming and phase-aware deadlines. These are application policies, not proof of a WSL transport ceiling. |
| Many small files each incur operation/helper startup, metadata, flush, hashing and receipt costs. Native Windows filesystem access to WSL is not a bulk-throughput guarantee. | Keep the current single-file path for its intended workload; measure the actual storage/filesystem crossing. | Compare manifest batching or staged archives against a persistent streaming channel. Select an alternative only after throughput/latency/permission measurements justify it. |
| Large-file integrity requires additional reads and CPU. A full destination temporary file may coexist with an older destination; the explicit 1 MiB copy buffer is not total process memory. | Allow destination disk headroom and verification time; do not infer low total memory or optimal throughput from the buffer size. | Add free-space preflight, quotas and measured transfer metrics; evaluate chunk integrity and sender/receiver streaming when it preserves end-to-end verification. Integrity currently takes priority over skipping validation reads. |
| Copying has no offset/chunk resume. Interruption can leave an owned partial, and publication before receipt persistence can remain unknown. | Inspect the retained transfer and its partial; explicit idle-session cleanup preserves the final destination. A matching authoritative receipt can confirm completion without recopying. | Introduce resumable chunk manifests bound to source identity/content and durable publication receipts. Never resume against an unverified changed source or treat cleanup as execution confirmation. |
| Progress records phase/bytes, bounded to at most twice per second; no established speed/ETA or bulk/low-disk guarantee exists. Transfers share the session's operation slot. | Follow byte/phase progress, tune independent session use within capacity and treat failure outcomes explicitly. | Qualify representative large/many-file/low-disk scenarios, then expose measured rate/ETA and a bounded transfer scheduler if useful. Avoid synthetic precision or flooding history. |
| The WSL filesystem transport checks its default filesystem user matches the endpoint user. Path traversal, symlinks/reparse points and protected runtime/data destinations are refused; concurrent external path replacement remains outside a complete isolation guarantee. | Use the intended distribution/user and explicit real workspaces; do not bypass refusals or change global WSL defaults as a shortcut. | Qualify a helper-owned streaming transport and handle-based path validation for a stronger boundary. Preserve confinement rather than permit arbitrary links or cross-user filesystem access. |

The [transfer reference](../developing/file-transfer.md) explains the actual Windows filesystem/WSL 9P mechanism and integrity/publication behavior. Relay neither creates that underlying socket nor treats it as a generic SSH/SMB transfer service.

## Monitoring, history and MCP retrieval

| Current boundary and effect | Available handling | Possible evolution or chosen priority |
| --- | --- | --- |
| Session conversation shows retained relay exchanges, not a complete native transcript or activity from every external client. Another client sees only its bound identity/project scope. | Use the correct authorized connection and follow the retained project/session context. | Add opt-in connector-specific transcript/event import, preserving authorship, privacy, scope and provenance. Do not imply that shared results transfer a model's hidden reasoning or complete conversation memory. |
| The monitoring window is passive follow-up; native inbox import/readiness inspection are explicit actions. Independent messages can remain unimported until the appropriate read. | Import/read through the authorized MCP or diagnostic action and keep the caller-owned inbox cursor. | Offer opt-in bounded background ingestion or scoped subscriptions with visible freshness/cost. Passive browsing currently takes priority over unrequested native contact and hidden side effects. |
| Histories are bounded/filtered pages, not an exhaustive single response. MCP and pipe frames are capped at 1 MiB; journal pages use a 400 KiB budget and bounded counts. Tool text/path fields have their own schema bounds. | Follow cursors, clear inappropriate filters and use previews/targeted details. Keep file bytes outside MCP messages. | Add bounded detail/artifact streaming, explicit truncation metadata or subscriptions. Preserve finite memory/response budgets rather than return unbounded logs. |
| Examining an alert records a revision-specific acknowledgement, not deletion, approval or execution repair. Changed failures can appear again. | Find the original outcome in project Activité; handle the actual underlying failure separately. | Add optional owner/snooze/resolution annotations if useful, kept separate from immutable outcome facts. Trustworthy history takes priority over making a failure disappear by rewriting it. |
| There is no automatic retention/compaction policy for ever-growing histories; long-running scale is not established by a small qualification fixture. | Monitor storage and back up the selected data; keep configuration and data out of published artifacts. | Add explicit retention/export/archive policies and measured database maintenance with scope-preserving retrieval. Choose deletion/retention rules with the user rather than silently discard history. |

## Installation, updates and delivery

| Current boundary and effect | Available handling | Possible evolution or chosen priority |
| --- | --- | --- |
| The portable package is unsigned; private releases require authorized repository access. WebView2 and native WSL/client prerequisites are not installed automatically. | Use the approved release, checksum and explicit preparation path; explain actual missing prerequisites/login. | Add signed distribution and an explicit prerequisite-aware setup flow when justified. Access may evolve by publication decision; preserve deliberate installation over hidden system changes or security-prompt bypasses. |
| The .NET runtime is bundled, so a global .NET update does not update the package's own runtime. Clean-machine prerequisite installation is not established by the extracted-archive check. | Track package versions, use approved updated releases and distinguish existing-runtime tests from a fresh-machine installation. | Add pinned runtime update monitoring and repeatable clean-machine/CI qualification, releasing refreshed archives after tests. Bundling currently favors predictable startup without asking users to install an SDK. |
| Absolute MCP launch paths/connection references need regeneration after moving an installation or changing its selected identity. Already connected clients do not silently reload; their supported lifecycle varies. | Keep the data scope explicit, regenerate/review fragments and use the actual client's supported reconnect. | Add connector-specific registration/lifecycle helpers or a stable installer-managed launcher. Preserve explicit identity and unrelated client settings; do not force-kill a client to simulate reload. |
| Separate data scopes create separate relay instances/icons. Portable startup registration and automatic update are not supplied. A duplicate process for the same scope reuses its existing owner. | Use the intended launcher/data path consistently; close/quit the correct instance. | Add a scope/instance picker, clear instance labels or an opt-in stable installation/startup mechanism. Keep multi-instance support deliberate instead of conflating unrelated data. |
| Upgrade/rollback needs an idle, backed-up data scope. Schema changes, protected credentials and active clients cannot be handled by blindly overwriting binaries or copying a live database; the developer publisher's busy guard is not a transactional cross-client drain. | Quiesce the selected host/clients, preserve the old version and data backup, then verify the new version before retiring rollback material. | Introduce a drain/maintenance protocol, versioned migrations and a packaged updater with atomic rollback of data and credentials together. Preserve durable work rather than prioritize unattended replacement. |

For actual initialization, connection export and upgrades use the [portable guide](portable-release.md); for the user's monitoring actions use the [functional guide](mvp.md). These guides describe the current route; future options above require separate design, authorization and qualification.
