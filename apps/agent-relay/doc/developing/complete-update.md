# Complete portable update

**Utility:** defines the single update transaction, readiness and recovery boundaries.  
**Usage:** use for an existing portable installation. Explicit initial activation is handled by this same command; a new installation or changing data scope remains separate. Development qualification never authorizes a stable deployment.

## Owners and input

One stable installation retains its root, data, projects, permissions and startup preference. Both remote releases and local packaging supply the same reviewed archive, SHA-256 and portable verification. Never copy a checkout directly over a running installation.

InstallationUpdate owns the existing exclusive journal and transaction. Its selected-release implementation uses schema 2; schema-1 journals retain recovery compatibility. InstallationSnapshot owns coherent C# database/configuration/credential snapshots and restoration. SqliteWorkStore owns maintenance-work checks; update additionally blocks uncertain work. InstallationRuntime is the narrow host/startup-status adapter. It obtains PID/start time over an authenticated host handshake and checks the exact process image immediately before stopping that idle host. No process-name guessing, client kill, request replay or model call is an update step.

The [minimal transport](mcp-transport.md) owns stdio and cooperative succession. complete_update.py adapts reviewed archive acquisition and invokes the same C# transaction; it does not duplicate its schema-2 phases. Its legacy typed-tool probes and reload callbacks are not used for the generic surface. The old stable_update_wait receipt entry delegates to this procedure once; it has no client-exit loop or fifteen-minute expiry.

## Paths and preflight

`McpDeploymentAdmission` owns the durable promotion marker, its path and the short cross-process admission lock. The updater closes admission and refreshes the admitted-transport snapshot within that lock, including clients arriving after preparation. The gateway registers successful initialization under the same lock and checks it again before forwarding each operational request. New clients and new requests receive `deployment_in_progress`, the deployment identifier, `execution: not_started` and `wait_for_deployment`. Admitted host work drains through `PromotionAdmission`; connection presence is never an authorization or a replacement for this work check. Refused/uninitialized connections cannot hold transport readiness hostage. Existing connections retain only passive transport controls and local deployment status while suspended; host identity inspection remains an authenticated read-only deployment control.

The marker survives interruption, independently of the short lock, and only the same validated transaction reopens admission after readiness or coherent rollback. Connection diagnostics retain instance/binding, client name/version, connection time, process identity, generation and activity without request payloads or credentials. Names/versions are untrusted bounded labels. Older transports must still acknowledge the selected successor; their pre-update behavior cannot be retroactively changed by a candidate. The existing host work barrier and transport readiness checks remain mandatory during that transition.

`complete_update.py --action status --data <data>` reads the atomically published C# journal without taking the driver writer lock. It remains usable during an update; resume and rollback retain exclusive ownership. The gateway's existing `get_connection_status` reports suspended admission locally without creating a worker or starting the host. A freshly refused MCP initialization does not become a control connection; use the local CLI for recovery. This changes neither participant grants nor deployment authority.

If `awaiting_transports` persists and Windows has demonstrably reused the PID of a recorded transport, the source maintenance command `tools/retire-reused-transport.ps1 -DataDirectory <data> -InstanceId <id>` previews the identity proof. `-Apply` retires that one presence only when the retained transaction requires it and Windows reports a newer process with a different image name. The exact original record and proof are retained beside the transaction under `transport-reconciliation`. The command leaves Windows processes and the update journal alone. Ordinary stale or unreachable live transports still require their normal recovery; age alone is insufficient. After a successful retirement, let the active continuation observe it or resume through `complete_update.py` if no continuation is running.

RuntimePaths owns the immutable release slot below the installation's var/apps/agent-relay/releases, the explicit transport selection and transport state locations. New slots use a compact 32-hex manifest prefix to leave room for Windows desktop assembly paths; the full manifest hash remains authoritative and an existing different manifest refuses. Known legacy full-hash slots remain valid for retained recovery; path calculation/recognition has one owner. A candidate's app/ and transport/ payloads are staged into its checked slot; root documentation/commands remain transaction-owned files. Old loaded files are retained rather than overwritten. Retention is recovery/cleanup material, not another selected stable version. Developer local/ outputs and user project workspaces are never internal prerequisites or distribution files.

The candidate must contain the independent self-contained transport, current MCP identity and operation revision manifest. Every source file/hash is checked, same-version different bytes are refused, reused operation revisions cannot change schemas, and incompatible wire requirements refuse before cutover. When native helpers change, candidates with the native maintenance adapter reconcile owned named-session roots inside the same update transaction. Candidates without that adapter retain the refusal if the data scope has retained sessions. Unchanged helper sets require no native inspection.

Native replacement runs under suspended admission with the relay host stopped. The updater selects named sessions from the stopped SQLite snapshot, verifies each Linux owner and requires its dedicated tmux process to be stopped. A live or unreadable native runtime refuses with the affected session identity. The updater never interrupts or replays a native request to satisfy that check. Stop affected native sessions at the coordinated safe point using their supported lifecycle procedure, or keep the earlier release available.

The update retains and hashes every before-image before authorizing publication. WSL accepts only captured or staged bytes, including a mix left by interruption. Forward resume completes the checked replacement. Rollback restores the original bytes and removes helpers absent before the update. A foreign change or unverifiable rollback retains admission suspension for diagnosis. The existing standalone sync command shares this filesystem adapter and stays available for explicitly selected maintenance.

A normal schema-2 update requires an existing qualified transport selection. For the first activation, explicitly select `--initial` and coordinate a safe maintenance point with consuming agents. The same C# transaction stages the candidate and retains that intent, suspends new admission, waits for active and uncertain work, and only then requests graceful closure of legacy connections. It waits for closure before stopping the host or publishing anything. It does not relabel the old broker as a new transport. Rollback restores the original pointer and absence of a transport selection through the same snapshot owner.

If the old authenticated handshake lacks process metadata, the existing `host_identity` adapter resolves the exact executable/argument/data owner, reads its OS start time and rechecks the scope. Only explicit initial preparation accepts that proof. C# retains it in the activation and revalidates PID, exact start time and image before any stop; normal updates continue using the authenticated handshake. Missing, ambiguous or changed identity refuses without stopping a process.

## Command and phases

After the exact archive is verified, use the existing complete_update.py entry with --data, --release-directory and --version. Its --action status, resume, rollback and diagnostic actions need no original archive after verified staging. Packaged launchers call that same adapter. Common registration/startup/UI integration and final archive qualification must be complete before deployment; source fixtures alone are not installed readiness.

From a clean checkout with its stable version committed, one command prepares and deploys the source through existing owners:

```powershell
python -B apps/agent-relay/tools/complete_update.py --source --data <existing-stable-data>
```

The first activation uses that same command with `--initial --codex-config <shared-settings> --workspace-config <development-settings>` and, if needed, `--stable-server <existing-stable-name>`. The explicit settings paths and stable binding are retained before execution. `--source` reuses a matching exact-source qualification receipt; otherwise it invokes the existing isolated `qualify` command, rather than implementing another packager or verifier. It creates no tag or remote release. An explicit verified archive remains supported through `--release-directory` and `--version`.

The CLI follows the retained runner until completion or an explicit attention error. On first activation it then invokes the existing paired registration adapter: the shared `agent_relay` uses the C#-generated fixed launch entry, the development connection remains workspace-local, and the stable data and binding must match. Resume uses the retained inputs and paired plan, including after interruption between the application and settings steps; an external settings change refuses with retained diagnostics. A configuration failure is not reported as full success. Neither the adapter nor the updater restarts Codex. Verify the consuming chat's actual catalogue and scoped access before telling it to resume work.

When explicit initial activation selects a corrected candidate while an earlier candidate is still only prepared/awaiting work, the same command asks the C# owner to cancel that unpublished preparation first. C# verifies the pointer and before-images and keeps the working old host intact. A published/uncertain recovery phase is never silently replaced. Retained runtime binding is shared by resume, rollback and authorization, so cancellation uses the same verified legacy identity and startup controller as activation.

Default command output contains bounded state and receipt references; `--details` explicitly requests the full retained transaction. Full diagnostics and generated reports remain outside Git.

An automatic rollback after failed activation is a failed deployment (nonzero CLI result with retained details), never a successful completion. Explicit `--action rollback` still reports successful recovery when that requested operation finishes.

1. Prepare a checked private candidate and independent recovery runner under the existing update directory. The same candidate resumes the same transaction; a conflicting candidate refuses. Completed before-images are never replaced.
2. Persist the owned admission barrier and awaiting_work state. Drain admitted requests and block on pending/running work or uncertainty created or changed since this transaction began. Earlier unknown outcomes remain retained history: preserve their exact state and data, never label them successful or replay them. Missing/invalid timestamps block rather than being treated as history. The host must confirm quiescence, and retained native helpers/workspaces are still protected by compatibility checks. Waiting survives interruption with no expiry and never stops/replays active work. Repeated resume uses the same boundary.
3. Stop only the verified idle host, take exclusive data ownership and capture the coherent SQLite backup plus protected configuration/credentials. A partial capture uses its own private directory; a completed snapshot is verified and immutable. A missing original snapshot after publication is a recovery error, never an invitation to take a new snapshot of changed data.
4. Publish all immutable slot bytes and managed root files, retaining verified root-file before-images. Persist selecting intent, then publish the checked runtime/transport selections and contract history behind the admission barrier. Known before/after values are reconciled; observed external changes refuse. The two files are not claimed to be simultaneously visible or protected from uncooperative same-user writers by OS compare-and-swap.
5. Start/verify exactly the selected host, authenticated version/contract, preserved configuration/credentials and startup preference. Await every expected live transport identity, and reject any current mismatching transport. Idle gateways change cooperatively without another client message. An acknowledgement gap retains awaiting_transports and the barrier, not a partial-success result.
6. Persist reopening intent before releasing the barrier. That irreversible boundary prevents old-snapshot rollback even if the process dies before recording complete. Resume finishes selection/readiness/release without restoring a database over newly admitted work. Repeating a completed matching transaction is a checked no-op.

Selection checks use the exact manifest; a metadata file alone is not proof that required old code stopped executing. Diagnostic transport leases are observations, never credentials or execution authority. No complete-update claim implies that an already-loaded legacy client was migrated.

## Recovery and errors

Before reopening intent, failure restores coherent prior selection, protected data and managed root files, verifies prior host/startup behavior and waits for required transports to return. Immutable failed candidate bytes remain retained for diagnosis/guarded cleanup; they are not selected. Cancelling while awaiting_work leaves the working old host alone. After admission may have reopened, restoring an old database is refused; inspect retained results and use compatible forward recovery.

Only this transaction's barrier can be removed. Unknown schema/phase, missing snapshot, conflicting file/selection or failed restoration retains a retrievable error and admission protection. Flushed intents and same-volume atomic file replacement support process-interruption recovery; process-exit tests are not power-loss certification.

Expected and unexpected CLI failures use the existing C# InstallationUpdateDiagnostics owner: code, diagnosticId, safe message, recovery and retained details path. Retrieve through --action diagnostic with its ID. Logging failure is explicit and preserves the primary error; rollback failure preserves both causes. Do not put credentials or complete agent requests in public diagnostics.

## Useful qualification

selected-update exercises real files/SQLite with a runtime adapter fixture: busy/uncertain drain, immutable slots, transport acknowledgement, idempotence, coherent rollback, actual child exits after stop/selection/reopening and preservation of work after admission. installation-runtime verifies authenticated PID/start time/image, quiescence and exact owned-child stop on a real isolated host. The retained schema-1 installation-update scenario protects legacy recovery. Full portable-host/transport/archive qualification is a separate delivery gate; no test authorizes a stable deployment, existing-agent work or global startup modification.
