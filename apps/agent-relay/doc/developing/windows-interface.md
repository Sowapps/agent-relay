# Windows interface

**Utility:** defines the monitoring UI, rendering boundary and lifecycle ownership.  
**Usage:** read before changing presentation, runtime packaging or interactive qualification.

## Presentation ownership

ProjectWindow is the C# monitoring host. Presentation/RelayWebView owns the embedded WebView2 control and its local resource boundary; Presentation/PresentationSnapshot owns passive data projection. Presentation/Assets owns the production HTML, design tokens, CSS, components, views and controller. Repeated cards, rows, filters and overlay drawers have one owner. The versioned [navigable prototype](../../prototype/README.md) embeds those same presentation components with a fictional host bridge and exterior simulation controls. Correct an isolated prototype draft first, inspect/qualify it, then promote the same assets and deliberately record the reviewed reference. Historical ignored prototype sources are not a second maintained renderer.

Every list uses a meaningful section heading and short purpose/usage introduction, followed by filters, contents and counts/pagination. Single-list tabs avoid a redundant panel heading; multi-section settings keep a panel introduction and individual section headings. General and project settings share the project tab component, selected underline, keyboard arrows/Home/End, roving focus and associated tab panels. Breadcrumbs follow explicit routes: General, Settings and Diagnostic are independent entries, while project tabs retain their project context.

Background observations reconcile existing DOM nodes by stable identity instead of replacing the page. Open details, focus, selection, drafts and scrolling survive updates in the same context; actual navigation resets the relevant context. Volatile broker heartbeat timestamps do not invalidate a whole presentation snapshot, but semantic connection changes and scope revocation still do. Modal actions use a shared top separation; failed rename actions retain the editable draft and show a contextual error. Known stale project confirmations are refused before submission; the host's admission/write locks and expected lifecycle checks remain authoritative.

Diagnostics distinguishes declared configuration from an observed success, stale result, unavailable check and failed check. Unverified/declared states have neutral indicators and explanations. The page performs no automatic model/environment readiness probe. Recent MCP records describe those exact broker clients, not the availability or login of every agent. The single-owner lock applies to the selected data directory; there is no fixed claim that all installations together contain one process. Environment facts come structured from composition (connection type first, distribution/user/host labeled); project workspace paths are displayed separately according to actual grants. Agent connector and project role remain separate.

The sidebar provides General, relayed projects, Settings and a persistent relay indicator. General contains metrics, an inline-action alert, the Work stream and project tiles. A project contains Summary, Tasks, Activity, Messages and Sessions; Summary shows metrics, current/recent tasks, recent messages and compact context. Filters belong to their history section. Advanced filters and diagnostics remain collapsed. Details use a right overlay/backdrop, independent internal scrolling, fixed header/close control and contextual footer; they do not shrink or reflow the underlying page.

List actions use the shared iconButton component with both an action title (mouse hover) and an aria-label. Provide direct project and settings access without forcing an intermediate page.

Interactive surfaces use their component-owned subtle hover backgrounds. Do not add a global brightness filter or inset hover border: those darken content and box entire task/message rows. Preserve intentional resting control/card borders and selected states. Tabs retain a rounded blue background and active underline; their labels are not selectable text. Outlines identify keyboard focus only; row/message/task-event outlines use an inward offset so parent-card clipping does not hide them.

Settings offers read-only connector/connection/permission context and a collapsed administration/diagnostic section with refresh, project editor, legacy history, technical console and Quitter. The TechnicalConsoleWindow remains the separate manual operation/binding surface. Native dialog controls retain UiTheme/MonitorComponents; they do not duplicate the monitoring page layout.

## Runtime and local resource boundary

Microsoft.Web.WebView2 is centrally pinned with locked NuGet content hashes. Restore uses the private workspace SDK/cache. The Windows project copies presentation assets and the WinForms/Core bindings plus x64 loader into the content-addressed runtime. The package also supplies a WPF binding: the application-local build target removes that unused reference before assembly resolution; warnings are not suppressed.

An installed Evergreen WebView2 runtime is required. It is discovered, never installed automatically. A missing runtime or failed presentation displays a native diagnostic/quit fallback while the relay/MCP lifecycle remains independent. Browser data lives under the selected relay data directory in presentation-cache. It is cache/preferences, not project history or credentials; do not put it in the executable staging tree. Runtime installation/update remains outside ordinary application startup.

The control maps only the presentation asset directory to https://agent-relay.invalid/index.html. It rejects navigation away from that page, nonlocal resources, popups, downloads, permissions, host objects, browser context menus, developer tools and browser accelerator keys. CSP allows local scripts/styles/images and denies network connections, frames, forms and objects. Untrusted message/result text is escaped. The UI receives no native binding credentials. Its bounded message bridge selects explicit application actions; it cannot submit arbitrary pipe requests, shell commands or scripts. The native action handler validates retained IDs and project/session capabilities; application policy remains authoritative. Ordinary monitoring never polls native diagnostics. An explicitly requested archive is a separate host use case with periodic passive verification until completion/cancellation.

## Data and scope

Core MonitorProjection groups operations by project/task identity. Replies link only to an actual message operation with matching project/session identity. Independent reports never acquire a fabricated request/task. Presentation task IDs include the project ID. Historical workspace/program/argument context comes from retained execution data rather than current command rules. Provider and environment are separate descriptors: views never branch on Codex/Claude/WSL names. Unsupported connectors remain readable with unavailable actions omitted; role alone grants no action. Disabled projects expose no session controls.

PipeMonitorSource uses authenticated administrator-only observe_* retained reads. They do not import native inboxes, inspect agents, reconcile transfers, execute commands or prompt models. A green relay indicator confirms observation of the local relay, not agent authentication or an external client's MCP connection. Session/connector state remains unverified or retained until explicit inspection. This window cannot attest that another MCP client has connected successfully.

Reads use bounded 50-item/400KiB pages; visible lists initially show five rows. Histories/reset use all-history; summaries distinguish visible, matching and loaded counts, and badges describe loaded context. Empty states explain filters and offer reset. Session date filtering uses last retained activity, or no date if none is available. Filters apply to loaded data. Partial operation history is labelled; load-more follows retained cursors. Newest-head refresh and older pagination have separate state. A burst with no overlap reopens pagination; older active operations remain watched through passive exact reads. Monitoring message cursors are newest-first and independent of operational MCP inbox consumption. Read/unread acknowledgement is unavailable in the retained journal, so the UI reports received message counts rather than inventing unread counts.

The host refreshes configuration scope before observations and removes deleted projects. Unchanged data does not rebuild the view. Changed snapshots preserve search focus/selection, scroll and open details. Full operation details survive unchanged previews; changed outcomes invalidate that retained full version. Async detail replies only refresh the currently matching drawer. Failed refresh keeps retained rows and exposes relay uncertainty. Unknown work never offers replay. Native approval stays in the native agent session.

Messages/results provide copy before optional technical data. Technical operation details expose passive events and explicit partial-file inspection; cleanup remains in the technical console. Session rename/close/reopen/inspection and interruption reuse existing authorized application use cases with the session owner as acting participant. No page navigation invokes them.

## Session conversation

The conversation page is scoped to project/session and reachable from session list/detail and operation/message details. ProjectObservation carries an optional session ID; the same passive reader requests bounded observe_operations/observe_messages pages with independent session cursors and no native inbox import. One selected thread refreshes passively; leaving it stops that subscription. Loaded rows merge by identity into retained project context while preserving newer revisions. Thread metadata exposes loaded/partial/error state; revoked project contexts are removed. Earlier thread pages load explicitly, separately from ordinary project pagination.

The presentation model orders actual request, result/state and message events chronologically. It suppresses a duplicate result when the exact correlated reply is present; independent messages stay distinct. It never joins another project/session or invents native transcript text. Previews are labelled and link to exact retained operation details. Unknown session activity dates are not replaced with today.

All clickable monitoring controls have visible hover and keyboard focus treatment, including active navigation and segmented tabs. A reviewed-operation notice links directly to all-history/all-state project activity and the retained drawer; the cross title describes that path.

## Examined attention items

The operation alert exposes an icon-only cross with accessible name « Marquer comme examiné » and a title explaining both the action and project/activity/all-history destination. Its detail drawer retains the explicit text label on a bordered, contrasted primary button. Both use the same acknowledgement action. It removes that exact operation revision from the alert, General attention count and « À suivre » task/operation filters. The ordinary history keeps the original outcome and marks it « examiné ». This action confirms review; it does not resolve an error, approve native work, cancel or replay anything.

AttentionReviews stores a versioned attention-reviews.json file under the selected relay data directory, outside SQLite journal facts and outside presentation-cache. Entries are scoped by project/operation and hashed state, exact UpdatedAt ticks and error code. A new revision no longer matches and becomes visible again. The native action passively reloads the retained operation and compares the displayed token before an atomic, flushed file replacement; a stale drawer cannot review a newer outcome. The browser changes its display only after native success. Full operation-detail caches preserve updated review state.

Review confirmation is a compact status toast: short text plus a history action aligned on the right, with wrapping inside the available width. The dismiss icon's tooltip retains the history location. Reviewing one operation removes only that revision from attention; the next unreviewed alert can replace it. Historical failure outcomes remain intact.

Human-facing dates use DD/MM/YYYY with2/2/4digits. Times use24-hour HH:mm or HH:mm:ss, with2digits per component; seconds are contextual. RelayComponents owns browser formatting and DisplayDateTime owns native/technical-console formatting, independent of display culture and using the local timezone. Lists reserve the full date's intrinsic width; message/task timelines and details include time, conversations/events retain seconds. Dates are absolute; any future relative wording must refresh automatically. Structured ISO timestamps, original user messages and raw diagnostic payloads retain their original machine/content representation.

General settings have Général and Projets scopes and no implicit last-project selection. The project directory lists active and archived projects with titled icon actions for open/settings/archive/reactivate/cancel-pending; configuration forms do not appear there. Each project's Réglages tab remains inside its explicit project route and active navigation context. Current workspaces are selected by that project's granted workspace IDs, never merely by a shared participant. Archived entries leave normal navigation/general activity but remain openable from the directory with a visible read-only history banner. Native lifecycle acknowledgement, pending/refusal state and refresh use the shared modal/toast/bridge components; the browser never changes persisted state before native confirmation. The server remains authoritative even if a client snapshot is stale.

A damaged/unreadable review file hides no alerts and is preserved; the interface reports a warning instead of silently overwriting it. One running host owns the data scope. Review status is a local administrative monitoring preference; existing participant MCP history/outcomes remain unchanged. Deployments preserve the file in place, and restarting the application reloads it.

## Lifecycle and identity

The top-level monitoring window opens maximized. Its restoration rectangle is centered at85% of the selected screen working area's width/height, excluding the taskbar. Bounds are calculated on first load after native DPI scaling, without multiplying physical working-area coordinates again. The minimum is capped to that rectangle on small screens. No window size/position/state is saved between launches. Tray activation preserves the current in-process maximized/normal state; minimized windows are recovered maximized. Embedded rendering/qualification surfaces retain their explicit size (evidence `2026-11-01-window-opening-geometry`).

TrayContext owns the NotifyIcon, window and relay shutdown. ProjectWindow raises QuitRequested; Settings/Quitter and the notification menu reach the same exit. The window X hides it. Relaunch with --show activates the existing host through the authenticated administrative show_window action, creating no second host or icon. The data-directory file lock remains authoritative. Closing the UI does not kill independently owned agent sessions or replay uncertain work. Automatic startup is read-only in this monitoring surface and is never enabled implicitly.

UiTheme owns native identity assets. The executable/notification area use the committed multi-size ICO generated from Assets/agent-relay.svg. The HTML brand uses the same opposite-arrow identity at its own size. Regenerating committed raster/ICO assets uses tools/generate-icon.py; ordinary builds need no image generator. Resource embedding and process single-instance tests do not establish a visual notification-area-shell check.

## Reproducible qualification

Build/test with the normal application commands. tools/prepare-conformance.py checks the versioned prototype reference hash and prepares identical fictitious data for ten relevant views. tools/check-interface-conformance.ps1 captures those views at 1120x728 and960x648 through the production C# RelayWebView. The targeted monitor-feedback scenario additionally checks panels across repeated snapshots, DOM identity, focus/selection, tab keyboard behavior, modal spacing and rejected rename drafts, with own-surface captures at1120/816pixels. Inspect captured images as well as machine checks; passing functional tests is not operator visual acceptance. Repeat only checks affected by subsequent changes.

For startup qualification, build the tests and explicitly prepare a self-contained Windows payload, then run `apps/agent-relay/tools/test-startup.ps1 -PayloadDirectory <absolute-local-payload-directory>`. It exercises the production controller/native preference adapter using a fresh space-containing data path and a temporary HKCU Run entry, removed in finally. It checks enable/disable, injected write/read failures, retry, compact rendering, the retained native startup bootstrap, duplicate ownership, source launch arguments and missing-target refusal. It does not enable the operator's scope or restart Windows. Successful runs keep reports/captures and discard their bulky test runtimes; failed runs retain diagnostics. A bounded child process is allowed to finish independently after a failed test.

Startup belongs to the Windows composition layer, not project capabilities or MCP participants. IStartupPreference separates the display from the Windows adapter; confirmed state may be unknown. Its registry name is stable per normalized data path. Enabling prepares a retained self-contained native bootstrap in data/startup-launcher before writing Run; disabling removes only that named value. The bootstrap's startup mode reads the current mcp-runtime.json and launches tray without --show, with no console, supporting native portable or explicit dotnet/assembly pointers. Same-volume hard links are used only for immutable staged payloads; normal portable installations use retained copies. There is no Python/shell dependency in the registered bootstrap. Keep this launcher while enabled, include its runtime in deliberate security maintenance, and never treat it as a disposable versioned build output.

The registered command names only the retained executable and startup mode; its data scope is derived from the parent of that bootstrap directory, avoiding a duplicated absolute path. Explicit --data-dir remains supported for controlled diagnostics. Commands beyond the [Windows Run limit](https://learn.microsoft.com/windows/win32/setupapi/run-and-runonce-registry-keys) are refused before registration, with a shorter-location explanation.

render-interface-check.ps1 with an explicit running data directory passively renders real General/Project/Settings/Diagnostics data through the same production host. These are separate test windows; no synthetic data enters the deployed application. WebView2 CapturePreview captures only its own content; desktop foreground capture is unnecessary. A control capture proves rendering, not tray gestures or user input. For interactive checks use Computer Use only against one exactly selected owned Agent Relay window. Stop on a locked desktop. Do not substitute unrelated foreground pixels for proof. Record automatic observations under application notes, awaiting operator validation.

## MCP client monitoring

Réglages généraux → Connexions MCP shows recent diagnostic broker leases: actual version, build/contract identity, catalog confirmation and current/outdated/closed state. It is separate from environment connections and conveys no authority. The retained broker, not the window, owns the lease. An explicit close creates a per-instance drain request; no credential is revoked, task replayed, or automatic client reconnect promised. Old facades without leases are not falsely shown as verified. Only the most recent256diagnostic records are loaded; stale heartbeats become offline. Detailed identities stay behind diagnostics.
