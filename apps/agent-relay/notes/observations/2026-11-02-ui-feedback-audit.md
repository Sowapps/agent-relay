# UI feedback: causes and correction plan

**Utility:** records the source audit of Florent's screenshots and the proposed correction sequence.  
**Usage:** implementation handoff; this audit authorizes neither UI changes nor deployment. Apply corrections to the navigable prototype first, then the application, after a separate GO.

## Scope and evidence level

Inspected the maintained prototype sources and generated standalone HTML, production HTML/CSS/JavaScript, native monitoring projection/actions, adapter descriptions, lifecycle conflict handling and existing UI qualification. No application or prototype code was changed, no browser/window was controlled, no model/WSL calls were made and no runtime/configuration was changed.

The screenshots establish observed defects. The findings below identify matching causes in source. No new interactive reproduction or runtime acceptance is claimed. Estimates are relative implementation complexity, not measured durations or token budgets.

## Diagnostic semantics to implement

Existing behavior to preserve: modal content is outside the snapshot-replaced view, so background snapshots do not currently replace its input directly; main/drawer scroll and ID-bearing open details have partial restoration already. Existing state_conflict/review_stale messages are already translated. The correction should complete these mechanisms, not claim that none exist or add a second independent owner.

1. Declared/configured: metadata is present, no availability check has been run. Neutral label and explanation; this is normal, not an error.
2. Observed available: say exactly what succeeded, for which scope and when. A broker heartbeat confirms that broker's presence, not agent login or workspace access.
3. Stale observation: retain the last result with its date and a clear freshness warning.
4. Check unavailable/unsupported: explain why and how to obtain more evidence; distinguish from an attempted check that failed.
5. Failed/permission denied: show the attempted check and the corrective action without raw JSON as the default explanation.

Do not run models, initialize agents, wake WSL or inspect arbitrary workspaces just to make a diagnostics page green. Existing scoped read-only observations can be reused; any new explicit check must state its effect and follow permissions. The current UI can truthfully show declared configuration without adding new probing functionality.

The actual number of independent tray hosts across scopes is not established by this audit. No global scan or process intervention is required to fix the misleading fixed counter.

## Common display rules

- Connection display: type first, named facts second. Example: WSL — Distribution: Ubuntu-24.04 · Utilisateur: sowapps. Show Workspace / Espace de travail separately with project context. Local — Dossier is appropriate only for an actual workspace row, not a whole endpoint with multiple granted paths.
- Use this formatting in diagnostics, project settings, project context, session drawer and operation context. Audit technical-console human summaries for the same ambiguity; raw diagnostic data remains raw and labeled.
- Each list gets a proper heading and a short useful introduction. Filters and counts use one composition; empty/loading/error states must be distinguishable.
- General and project settings remain separate. Opening a project setting keeps the project's navigation context. General project-directory actions keep titled icon buttons.
- Reuse existing tab visuals. Preserve the chosen native-window style, existing hover decisions, full date/24-hour formatting and neutral provider/transport boundaries.
- No framework/browser/package installation is required for these corrections. Preserve the native C# host and local WebView presentation.

## Execution sequence after implementation GO

1. **Reference and shared rules:** version the maintained prototype source/reference; reconcile affected existing routes before changing their visual details. Define route metadata, tabs, section headers, status/connection facts and modal spacing. Review the corrected navigable standalone prototype with simulation tools outside its frame.
2. **Interaction simulation:** add a deterministic “background update” scenario and a conflict/failure scenario. Expanded sections, current route, modal draft, focus and scrolling must survive simulated data updates. Verify the standalone artifact is regenerated from the same sources.
3. **Application projection and rendering:** apply the reviewed components, structured metadata, truthful diagnostics and targeted update/state preservation to production. Keep permission/scope enforcement and lifecycle authority in the host. Prefer an internal presentation change; no new MCP tools are needed. If U14 requires a public contract change, assign a new RC and qualify that change before deployment; do not reuse an existing deployed version for a different contract.
4. **Focused qualification:** compare prototype/app using identical fictitious data at 1120×728 and 816×728, plus maximized rendering. Cover every tab/section listed above, text wrapping, long paths and modal action spacing. Inspect the app's own captured surface, never the desktop or unrelated apps.
5. **Delivery:** document current behavior, record observations, commit/push on a dedicated branch, merge and deploy the approved correction scope with the standard command. Verify data/permissions unchanged. No new tag or GitHub release without its own authorization.

## Minimal acceptance scenarios

- Open MCP Diagnostic and relay Technical information; deliver at least three snapshots/heartbeats; both remain open and at the same scroll position. Test two rows independently and disappearance of one row.
- Keep a list row or tab focused, select text and type a session rename; a background update preserves focus, selection/draft and scroll. Explicit navigation resets only intended route-local state.
- Demonstrate no whole-view replacement for an unrelated heartbeat. Semantic connection state changes still update, and removed/revoked scope is not retained as actionable data.
- Exercise neutral declared, verified, stale, unsupported and failed diagnostic examples. No unverified success dot, fixed global instance claim, false agent-login inference or automatic external probe.
- Inspect WSL and Local facts in every affected context with multiple project workspace grants, a long path and a missing field. No unlabeled combined string or invented path.
- Navigate all general/project/diagnostic routes and tabs with mouse and keyboard; confirm breadcrumb, selected tab, associated panel and focus agree.
- Simulate a rename rejection, stale review, project lifecycle conflict and vanished MCP client. Show the reason and safe next action, retain drafts and make no duplicate submission. Preserve existing no-replay behavior on uncertain completion.
- Verify headings/introductions/counts in tasks, activity, messages, sessions, general feeds, project settings, general project directory, MCP clients and diagnostics; confirm filtered-empty differs from genuinely empty/unloaded/error.
