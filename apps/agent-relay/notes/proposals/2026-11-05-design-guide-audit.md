**Utility:** records source-backed gaps and the proposed sequence for design guidance and structural corrections.  
**Usage:** read before authorizing the documentation or application lots below; observations are not operator acceptance or implementation permission.

Traced session admission → provisioning → native control; file validation → staging → publication; MCP catalog → dispatch → errors/version; passive UI → shared presentation/prototype; host publication/ownership; source and recovery conventions. These requirements are settled; proposed implementation mechanisms below are not.

## Existing strengths to preserve

- Core RelayApplication/WorkService/ProjectPolicy coordinate neutral use cases through ports; Core has no infrastructure project reference. Infrastructure depends on Core. This is a real dependency boundary, not merely folder naming.
- SqliteDocuments shares a bounded document capability; SqliteWorkStore separately owns operation/event transactions. Do not replace these with a speculative generic ORM or repository hierarchy.
- RelayJson, PipeFrames and RelayLocation already centralize serialization, framing and pipe identity. McpIdentity derives the contract from real tool definitions, envelopes and served guides rather than an independent handwritten contract number.
- Presentation assets and reusable components have one owner; the prototype builder embeds them with separate fictional fixtures. Preserve prototype-first promotion and native-only rendering verification.
- Project admission, policy pinning, durable work and fail-closed uncertainty checks are meaningful safeguards. Rechecking permission at admission and execution is not automatically duplication: revocation can happen between those times.

## Responsibility map and design direction

Use levels, not a mandatory number of services or assemblies:

| Level | Responsibility | Existing anchor / intended treatment |
| --- | --- | --- |
| Entry boundary | Parse, authenticate, validate request shape, adapt response | MCP facade, pipe, native UI bridge; no duplicated domain policy |
| Application capability | Coordinate a coherent user capability and its sequence/transaction | RelayApplication/session or project lifecycle; one service may expose several related operations |
| Domain policy / focused strategy | Own a rule or a precise behavioral variation | ProjectPolicy, admission rules; strategy for an actual variant, not every conditional |
| Ports / technical capabilities | Express what the use case needs without platform types | Sessions, journal, execution, recovery, inspection; keep cohesive interface sizes |
| Adapter / platform service | Translate that capability to a platform/client/storage mechanism | WSL, SQLite, local file publication; keep client connector distinct from environment connection |
| Library / operating system | Perform primitive I/O | Processes, tmux, filesystem, DPAPI; no business orchestration |

Composition is an outer responsibility. Shared capability code belongs at the lowest level that owns its meaning, not in a global Utils bag. Dependency inversion is about contracts, not requiring a DI container or interface for every class. Domain-independent helper reuse does not require routing all calls through every layer.

For A02, recommended candidate: one small versioned, packaged layout definition, accessed through C# and Python layout facades. Provisioning/control/migration/sync use those facades; fixture corpus checks UUID normalization, current/legacy recognition and rejection. Keep OS ownership, symlink and permission enforcement inside the responsible environment adapter. Shared facts are centralized; distinct OS security checks are not forced into one cross-platform implementation.

Alternatives: handwritten language-local constants plus tests still duplicate authoritative facts; generated language constants can be sound if generated from one owner but introduce regeneration checks; invoking Windows from WSL for each path introduces unnecessary platform coupling. Choose the simplest packaged-definition or generated-facade option after checking packaging/bootstrap availability. No speculative universal path engine or runtime network dependency.

For A03, retain a coherent session capability facade and extract substantial collaborators where useful: inbox import/correlation, command dispatch/recovery and file transfer already have distinct change reasons. Move construction to composition. Add adapter-selection mechanisms only to support actual bindings; future SSH/client support is not delivered by merely introducing an interface. No service-per-method, generic entity manager or base-class hierarchy is prescribed.

## Design guide and conventions to prepare

Proposed document ownership, to avoid another competing reference:

- doc/developing/design-guide.md: reusable reasoning for responsibility levels, SoC/SOLID/DRY, dependency direction, ownership of knowledge, collaboration between services/strategies/adapters, evolution and review examples. This is workspace practice, without WSL product details.
- Existing doc/developing/conventions.md: stable source conventions and short C#/Python/JS/PowerShell examples. Own naming, declarations/constructors, file organization/imports, formatting, nullability, async/cancellation, exceptions/results, serialization/encoding, comments and checks; refer to the design guide for reasoning rather than repeat it.
- Existing application projects-and-adapters/application-architecture/runtime-storage references: current capability map, actual composition and concrete rule owners. Clearly label legacy/demo compatibility rather than describe it as the whole app. Consolidate or redirect overlapping architecture material after checking its consumers; do not delete historical notes.
- Existing workflow and AGENTS entry points: short pre-change/recovery route, current authoritative guide and scoped workstream. Link only what an agent needs to proceed. Consumer MCP onboarding remains separate from repository development instructions.
- Application notes/decisions index: significant engineering decisions with context, decision/status, alternatives, consequences and supersession. Accepted current behavior lives in doc; the dated reasoning stays in notes. Operator decisions remain canonical root evidence, not copied into every ADR.

A reference is warranted when changing one element requires checking another that is not obvious from ordinary calls. Use C# XML see/seealso/cref where symbols resolve, Python/JS docstring @see with stable symbol/file names, PowerShell comment-based help links for entry points. Prefer symbols and invariants to fragile line numbers. Open/close references are reciprocal. Link shared layout ownership and provisioning/update/recovery partners explicitly; do not annotate every accessor, every call or every file. A reference must explain the relationship; shared implementation and tests remain primary.

Conventions must distinguish one-line trivial expressions from multi-step control flow, public contracts from internal helpers, expected failures from unexpected exceptions, wire timestamps from human display, and real product rules from test fixture values. Preserve current bilingual glossary, passive UI semantics, full human dates and24-hour times. Exceptions require a recorded reason and scope rather than silent style drift.

## Short-term and long-term operation

Short term: establish authoritative guides and a decision map, then correct the duplicated runtime/lifecycle knowledge and the demonstrated boundary/host issues. Keep every change small enough to review. For each lot record problem → cause → selected solution → affected consumers → useful checks → delivery/rollback, including uncertain observations.

Long term: before a change, locate the knowledge owner and the operations that must evolve with it; reuse existing capabilities, compare alternatives only when meaningful, update guide/decision status if architecture changes. While changing code, apply conventions to touched areas without unrelated reformatting. At completion or before compaction, persist scope, branch/commit, decisions, actual results, unresolved risks and exact next action. At resume, read AGENTS → current guide/decision → scoped checkpoint and inspect repository/goal state. Do not treat an old GO or historical test result as permission or fresh verification.

Keep progress in one scoped workstream; significant design reasons in the decision register; product truth in current docs; secrets and bulk test output out of Git. A passed machine check remains an observation until operator validation where required. Use a lightweight owner/paired-operation review on relevant changes, not blanket checklists or mandatory WSL/model tests. Existing memory failure of the goal tool must be reported as unavailable metrics, never invented consumption.

If a lot changes the public MCP contract or served guide contents, follow the existing stable/RC contract-version rule before deployment. Purely internal design notes do not warrant a new release or runtime deployment.

There are no newly found requirements needing a technical answer from Florent; routine implementation choices remain the implementer's responsibility within the next authorized scope. Avast, cleanup implementation and new product adapters remain outside this plan.
